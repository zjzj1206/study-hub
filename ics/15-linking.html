15 · 链接、目标文件与库

依据 2026-11-05 第 15 讲全部 65 页课件及本讲研讨单。主线是：源文件分别翻译为目标文件，链接器确定“名字指谁”，再修正“地址填什么”；程序装入后还可以动态装入库。练习见第二次测验，研讨与作业路线见附录 C。

本章先解决什么问题#

把“找名字”和“填地址”分成两遍。 先读编译链和 ELF，知道链接器拿到哪些材料；再判断每个名字在哪里定义；最后计算引用要填入的地址。库搜索和动态链接只是把“定义从哪里来、何时确定”进一步展开。

阅读时可先看本章各节的分步例子，再回到信号表、公式和边界说明核对；最后用第二次测验分章习题检验能否独立填写。

从源文件到运行：每个阶段解决什么#

  • 翻译单元：一个 C 源文件经过预处理后得到的编译输入，包括展开的头文件内容。不同翻译单元可以分别编译。
  • 预处理：处理 #include、宏与条件编译，输出仍为 C 文本，常用后缀 .i。声明来自头文件并不意味着对应函数实现已被复制进来。
  • 编译：进行语法、类型检查和优化，将 C 翻译成汇编 .s。
  • 汇编：将汇编翻译为机器指令和数据，产生可重定位目标文件 .o；同时输出符号表与尚未确定引用的重定位记录。
  • 链接：组合多个目标文件，进行符号解析、布局和重定位，产生可执行文件或共享对象。
  • 加载：建立进程地址空间并映射程序及依赖库；动态链接器完成所需动态重定位，再经启动代码进入程序。链接器和加载器不是同一个概念。
  • GCC driver：gcc 是驱动程序，根据选项调用预处理器、编译器、汇编器与链接器；gcc -c 停在目标文件，尚未完成最终链接。
输入→输出 观察命令 应该观察什么
main.c→main.i gcc -E main.c -o main.i 宏和包含文件展开
main.i→main.s gcc -S -O0 main.i -o main.s 调用和数据访问对应汇编
main.s→main.o gcc -c main.s -o main.o 二进制代码及未决引用
多个 .o→程序 gcc main.o sum.o -o demo 外部引用被解析
目标文件检查 readelf -h -S -s -r main.o 头、节、符号、重定位
带重定位反汇编 objdump -dr main.o 占位字节与重定位字段对应

一个可以手算的双文件例子#

main.c：

extern int sum(const int *a, int n);
int values[3] = {2, 4, 6};
int main(void) {
    return sum(values, 3) != 12;
}

sum.c：

int sum(const int *a, int n) {
    int total = 0;
    for (int i = 0; i < n; ++i) total += a[i];
    return total;
}
  • main.o 定义 main、values，引用但不定义 sum；sum.o 定义 sum。只编译 main.c 成 .o 可以成功，只用它生成可执行程序则会因缺少 sum 的定义而失败。
  • nm main.o 常见 T main、D values、U sum；T 表示代码，D 表示已初始化数据，U 表示未定义引用。具体偏移受编译选项影响，不应背某次构建的地址。
  • 模块化使代码可以独立维护；只改一个模块通常只需重新编译该模块并重新链接。静态库按目标模块提取，动态库允许共享只读代码页，是空间复用的两种方式。

三类目标文件与 ELF 的两个视角#

类别 主要用途 常见 ELF 类型
可重定位目标文件 .o 作为后续链接输入 ET_REL
可执行文件 作为程序映像的加载来源 传统非 PIE 为 ET_EXEC
共享对象 .so 加载时或运行时动态链接 ET_DYN
  • PIE 可执行文件也可使用 ET_DYN，因此 ELF 类型与文件后缀不是一一对应。
  • 节（section） 是链接视角的组织单位，如 .text、.data；节头表记录节名、类型、文件偏移、大小及关联信息。
  • 段（segment） 是加载视角的组织单位。程序头表描述映射范围、虚拟地址、文件大小、内存大小与权限；一个可加载段可包含多个节。
  • 不要把 ELF 文件偏移、输入节内偏移、链接后的虚拟地址混为一个数字。可重定位文件通常不需要用于建立进程映像的程序头表。
节／结构 内容与作用 常见误解
ELF header 位宽、字节序、文件类型、体系结构及表的位置 不是只存入口地址
.text 机器指令 不是 C 源码
.rodata 字符串常量、只读常量、部分跳转表 并非所有常量都一定单独保留
.data 通常为非零初始化的静态存储期对象 不是所有局部变量
.bss 通常为零初始化、未显式初始化的静态存储期对象 运行时占空间；文件中不存对应整片零字节
.symtab、.strtab 链接符号表及名字字符串 普通自动局部变量不靠它跨模块解析
.rela.text、.rela.data 代码／数据中的重定位位置、类型、符号、加数 修补的是目标节，不是把地址写进重定位表
.debug* 调试信息 调试变量信息不等于链接符号
.interp 动态解释器路径 不是所有依赖库清单
.dynamic、.dynsym 动态链接信息与动态符号 与完整静态符号表用途不同
  • x86-64 常见 .rela.* 显式保存 addend；课件概览中的 .rel.* 是泛称，REL 与 RELA 格式应区分。
  • .bss 常为 SHT_NOBITS：仍有节头和内存大小；“不占文件数据字节”不等于整个 ELF 中没有任何关于它的信息。
  • 装入后代码、数据、堆、共享库映射、栈构成虚拟地址空间；课件布局是概念图，ASLR、PIE 等会使实际地址改变。入口通常是启动例程，不是直接跳到 C 的 main。

符号：声明、定义、引用与可见性#

  • 定义 为对象分配存储或提供函数体；引用 使用某个名字对应的对象或函数；声明 告知类型与链接属性，不必产生实际引用。
  • extern int x; 通常只是声明；int x=7; 是定义；extern int x=7; 带初始化，仍是定义。不能把所有带 extern 的符号称为弱定义。
  • 非 static 的文件作用域对象和函数通常有外部链接；其他模块可引用它们。模块中未定义的被引用外部名字，需要由链接器寻找定义。
  • 文件作用域 static 对象／函数具有内部链接，是该模块的局部链接符号；不同模块可以各自有名为 x 的内部对象，不发生跨模块合并。
  • 函数内 static 对象有静态存储期，编译器可以为其生成独特局部符号，放入 .data 或 .bss；普通自动变量可在栈上、寄存器中或被优化掉，不应统一称为“局部链接符号”。
extern int remote;
int initialized = 7;
int zero;
static int private_count = 2;
int next(void) {
    static int count;
    int temporary = ++count;
    return temporary + remote + private_count;
}
  • 在不优化掉有关实体的观察条件下，initialized 是外部定义；remote 是未定义外部引用；private_count 与 count 是内部对象；temporary 不需要链接器在其他模块中找定义。
  • 单独声明但从未使用的函数不一定产生 U 项。普通链接器也不等同于 C 类型检查器：跨文件把同名对象声明成不同类型，即使链接成功，也不意味着程序正确。

从两个文件理解为什么编译成功仍会链接失败#

  • main.c 声明 int sum(const int *,int);，编译器由此知道调用参数和返回类型，因此可以生成调用指令；它无需此时已经知道 sum 的最终地址。
  • main.o 因为实际调用了 sum 而留下未定义引用。sum.c 编译出的 sum.o 则含 sum 的函数体与符号定义。
  • 链接器把 main.o 的引用关联到 sum.o 的定义，才解决“调用的是谁”。若缺少 sum.o 或提供该定义的库，前面的类型检查仍可通过，最后却出现 undefined reference。
  • 找到定义后还不够：多个模块代码被放进最终布局，sum 的位置可能变化，所以随后还要把调用位移修补正确。符号解析与重定位是连续但不同的问题。

重复符号：传统教材规则与实际工具链#

  • 普通强定义：例如非弱属性的函数定义、已初始化外部对象定义。两个同名外部强定义通常造成重复定义错误。
  • 显式弱符号：ELF 的 STB_WEAK；同名强定义可以覆盖弱定义。多个弱定义时，不应编写依赖某一个必然胜出的程序。
  • 暂定定义：文件作用域的 int x;。教材用传统 -fcommon 模型把它解释为可合并的 COMMON，并常以“弱”概括；COMMON 与 ELF 的 STB_WEAK 不是同一个编码。
  • 在 -fcommon 教学模型下，同名 COMMON 可合并，普通强定义优先；合并大小、对齐由工具链规则处理，不应据此让不同类型对象共享一个名字。
  • GCC 10 起默认 -fno-common，普通暂定定义通常落入 .bss，多文件重复 int x; 会报错。题目采用旧规则时须明示 -fcommon，复现实验也显式指定选项。GCC 官方迁移说明
模块 A 模块 B 约定／结果
int x=7; int x=9; 两个强定义，错误
int x; int x; -fcommon 下可合并；-fno-common 下通常重复定义错误
int x=7; extern int x; 并使用 x 一个定义与一个声明，正常解析
static int x=7; static int x=9; 两个独立内部对象
  • 规范组织：头文件放 extern int x;，恰好一个 .c 放 int x=7;；头文件也声明函数，并被定义和调用该函数的文件共同包含。
  • 使用 int f(void) 明确无参数；课程传统 C 模式下 int f() 表示未给出参数原型，不能拿它替代类型检查。注意语言版本差异。

重定位：先定位，再改引用#

  • 第一步合并／布局输入节，给相关符号分配输出位置；第二步按重定位记录修补代码或数据中的引用。
  • Elf64_Rela 的 r_offset 指示待修补位置；在本讲 ET_REL 例子中，它是目标输入节内偏移。r_info 编码符号索引与重定位类型；r_addend 是带符号加数。
  • 设 SSS 是符号最终地址，AAA 是加数，PPP 是被修补字段首字节的最终地址，下面给出本讲常见公式。
重定位类型 写入表达式 边界
R_X86_64_PC32 S+A−PS+A-PS+A−P 32 位有符号相对位移
R_X86_64_32 S+AS+AS+A 截为 32 位后零扩展必须还原该值
R_X86_64_32S S+AS+AS+A 截为 32 位后符号扩展必须还原该值
R_X86_64_64（补充） S+AS+AS+A 64 位绝对引用

为什么 call 的 addend 常为 −4#

  • call rel32 的 1 字节 opcode 后是 4 字节位移；CPU 使用下一条指令地址作为相对基准。
  • 若位移字段首地址是 PPP，下一 PC 就是 P+4P+4P+4。所需位移为 S−(P+4)=S−4−PS-(P+4)=S-4-PS−(P+4)=S−4−P，所以该布局中的 addend 为 −4。
  • −4 不是所有 PC 相对指令的普适常数，应从字段位置和指令末尾的距离推导。不能把 call opcode 地址代替 P。

课件 p.36 的重定位完整计算#

  • 已知 main 地址 0xBABF18，sum 地址 0xBABF40，array 地址 0xCAFE10。
  • mov 的地址立即数字段在 main+0x15，绝对重定位写入 0x00CAFE10，小端字节为 10 fe ca 00。
  • call 的 opcode 在 main+0x19=0xBABF31，位移字段在 main+0x1A=0xBABF32。
  • S+A−P=0xBABF40−4−0xBABF32=0x0AS+A-P=\mathtt{0xBABF40}-4-\mathtt{0xBABF32}=\mathtt{0x0A}S+A−P=0xBABF40−4−0xBABF32=0x0A，写入 0a 00 00 00。
  • CPU 执行时下一 PC 为 0xBABF36，加 0x0A 得 0xBABF40。必须同时用链接公式与 CPU 公式验算。
  • 未链接时 e8 00 00 00 00 反汇编成调用下一条，仅反映占位字节；链接器之后会修补，不能据此认定源程序真的调用了自己下一条指令。
  • 新工具链可能产生 R_X86_64_PLT32 而不是课件中的 PC32；它允许经 PLT 调用，也可能在最终链接时直接绑定。应阅读实际类型，不能强行套用某一版输出地址。

读题时先给每一个地址加上含义#

  • S 是被引用对象或函数最终放在哪里；P 是当前这段机器码中待修改字段放在哪里；A 是记录额外携带的常数修正。S 和 P 都是地址，A 则不是另一个符号地址。
  • 例如 opcode 在 0x401020，其后四字节位移从 0x401021 开始，目标在 0x401080。此时 P 必须取 0x401021，下一条指令地址却是 0x401025。
  • CPU 需要的位移是目标减下一 PC：0x401080-0x401025=0x5B。链接记录用 P 表达同一件事，便写成 S-4-P；−4 把字段首地址调整成字段末尾之后。
  • 写入机器码的是数值 0x5B 的四字节表示 5b 00 00 00，不是目标地址的四字节表示。最后把下一 PC 加上位移再验一次，能同时检查符号、端序和减数是否正确。

静态库：打包、提取与顺序#

  • .a 是多个目标模块的归档，不是简单把所有库函数事先揉成一个巨大函数。ar rcs libvec.a add.o mul.o 创建归档和索引；ar t libvec.a 列成员，ar x libvec.a 在实验目录提取成员。
  • 教材 GNU 链接模型从左到右处理输入：普通 .o 参与链接；归档按当前未解决引用提取需要的成员，并继续处理这些成员带来的引用。选择单位通常是目标成员，不一定精确到单个函数。
  • 未解决集合 U 随扫描而变化：某成员定义 U 中的符号时被提取；其定义从 U 消去，它的新外部引用加入 U；扫描结束仍有必需未定义符号则失败。
  • 若 main.o 用 A，库 A 的成员又用 B，应把提供者放在使用者后：gcc main.o -L. -lA -lB -o demo。把 -lA 放到尚无 A 引用的位置，通常不会自动为未来输入回头重扫。
  • 循环依赖可按需重复库，或用 -Wl,--start-group ... -Wl,--end-group 反复搜索；该规则限定普通归档搜索，不是说所有链接模式都一律只扫一次。GNU ld 文档

一次扫描中未解决集合怎样变化#

  • 假设 main.o 需要 f；libA.a 中某成员定义 f 又调用 g；libB.a 定义 g。处理 main.o 后，未解决集合是 {f}。
  • 接着处理 libA.a，提取提供 f 的成员，f 被解决，同时引入 g，集合变成 {g}。再处理 libB.a，提取提供 g 的成员，集合变空。
  • 若先处理 libB.a，当时还没有 g 的需求，其成员不会因为未来可能需要就全部装入。后面处理完 main.o 和 libA.a 才出现 g；普通扫描不会自动回头，所以链接可能失败。
  • “库放后面”不是需要死记的格式习惯，而是为了让需求先出现、提供者再接受搜索。有循环依赖时，这个一次扫描模型就需要重复库或 group 重扫来补足。

共享库与动态链接的三个时点#

  • 构建时：gcc -fPIC -c add.c 产生位置无关代码，gcc -shared -o libvec.so add.o 产生共享对象；链接应用时记录依赖和动态重定位信息，而非复制整个共享库实现。
  • 加载时：内核加载程序与解释器，动态链接器映射所需共享库并完成必要重定位；相关信息来自 .interp、.dynamic 等。
  • 运行时：程序主动调用 dlopen 装入插件，dlsym 获取地址，使用完后 dlclose 释放引用。dlclose 不保证在一切情况下立刻卸载。
  • 延迟绑定 是部分函数符号首次调用才解析，不等于所有动态重定位都延迟；也不等于每个函数调用都重新装入库。
  • GOT 可保存解析后的地址；PLT 是外部函数调用的跳转入口机制。本讲只需理解“间接引用使代码无需因加载基址不同而整体重写”，具体指令序列可后续展开。
  • readelf -d demo 查看 NEEDED，readelf -l demo 查看解释器和加载段；ldd demo 用于自己构建、可信程序的依赖观察。

dlsym 的检查顺序#

  • dlopen 返回空句柄时，用 dlerror 获取诊断。
  • 查找符号前先调用 dlerror() 清除旧错误，再调用 dlsym(handle,"name")，然后检查新的 dlerror()；仅凭符号地址为 NULL 不足以区分所有情况。
  • 得到函数地址后必须按正确函数原型调用。运行时查找绕过常规源文件类型关联，更需要一致的头文件接口。
  • 静态链接便于携带确定版本的实现，但程序体积和更新重链接成本较大；动态链接能共享只读代码页与集中更新库，但有运行时依赖和符号解析开销。不同进程的可写全局数据通常独立，不是因为使用同一 .so 就全部共享。

编译时 宏把 malloc 改为 mymalloc 源代码可重新编译 包装器自身不套该宏，调用真实 malloc
链接时 -Wl,--wrap=malloc 可重新链接的目标文件 __wrap_malloc 内调用 __real_malloc
加载／运行时 共享对象与 LD_PRELOAD 适用的动态链接程序 dlsym(RTLD_NEXT,"malloc") 获取后续定义
  • 编译时方案改写源级调用，不是改系统库本身；不要让包装器调用又被宏替换而无限递归。
  • 链接时 GNU --wrap 改写未定义引用，已经在同一模块内部绑定的调用不一定被拦截。
  • 动态插桩依赖符号可插入性；静态链接、内部绑定、编译器内联以及安全执行模式等都可能使 LD_PRELOAD 不适用。课件“任意动态程序”是教学概括。
  • 插桩可用于调用次数、分配地址追踪、参数检查、故障注入。课件给出的 malloc 中直接 printf 示例可能因日志路径再次分配内存而递归；实际包装器需要处理重入、初始化、错误保存和线程安全，不能把演示代码直接当生产实现。
